# Factory Engineer to Mission Control integration contract

## Decision

The V1 trust bootstrap is authenticated retrieval of an immutable Factory Deployment Package. Mission Control calls a preconfigured Factory Engineer HTTPS endpoint with a scoped, revocable service bearer credential, verifies the response independently, and maps it into its existing governed Mission/Plan draft path.

No shared database, arbitrary source URL, raw Markdown handoff, customer-data export, or direct execution is permitted. A signed portable file may be designed later as an offline secondary channel; it is not the primary V1 path.

The detailed contracts are:

- [Factory Deployment Package v1](phase-2/deployment-package-v1.md)
- [Authenticated retrieval](phase-2/authenticated-retrieval.md)
- [Mission Control trusted handoff](phase-2/mission-control-handoff.md)

## Ownership

Factory Engineer is authoritative for:

- package issuer, identity, version, immutable document, digest, status, and upstream approval;
- Customer Factory Model, current/target workflow, selected opportunity, readiness, economics, and decision pins;
- source-evidence references and approved deployment intent.

Mission Control is authoritative for:

- local operator/workspace/team/repository/code-scope authorization;
- Mission, Plan, WorkOrder, Task, Attempt, and runtime Factory Definition identity/state;
- workflow/runtime resolution, policy, execution manifests, models, tools, sandboxes, and leases;
- execution evidence, independent verification, approvals, acceptance, GitHub publication, release, deployment, rollback, and recovery.

Factory Engineer approval means “approved to propose for governed handoff.” It is never Mission Control Plan approval or execution/release authorization.

## Retrieval contract

```text
GET /api/deployment-packages/{package_id}/versions/{package_version}
Authorization: Bearer <opaque scoped token>
Accept: application/vnd.fdlc.factory-deployment-package+json;version=1
X-Correlation-ID: <UUID generated by Mission Control>
```

The response is a snake_case JSON envelope:

The package object is immutable and digest-covered. The attestation is current retrieval-time state and is outside the digest.
The response media type is exactly
`application/vnd.fdlc.factory-deployment-package+json;version=1`. Factory Engineer
validates `X-Correlation-ID` as a UUID and repeats the exact value in the retrieval event,
success attestation, or bounded denial body.

The full compact UTF-8 retrieval envelope is at most 256,000 bytes. General contract
arrays contain at most 200 items and requested code scopes contain at most 50 items.
Factory Engineer applies a 240,000-byte create-time cap to the target plus deployment
intent, leaving room for immutable lineage, issuer, approval, and attestation metadata,
then enforces the exact full-envelope ceiling before publication and on retrieval.

## Canonicalization

Both repositories implement `fdlc-canonical-json/v1`:

- ASCII object keys sorted recursively;
- compact UTF-8 JSON;
- array order preserved;
- strings, booleans, null, safe integers, arrays, and objects only;
- floats and unsafe integers rejected; decimals encoded as strings;
- omit only `package.integrity.digest` during calculation;
- SHA-256 rendered as `sha256:` plus lowercase hexadecimal.

The shared JSON fixture and adjacent digest in `fixtures/contracts/` are normative. Do not label this algorithm RFC 8785/JCS.

## Validation and freshness

Mission Control fails closed unless all of these hold:

- authenticated retrieval from its configured HTTPS Factory Engineer base URL succeeds within bounded timeout/size;
- media type and schema version are supported;
- issuer ID/type/environment/authority scope match configured trust;
- immutable package status and current attestation status are both `PUBLISHED`;
- package identity/version/digest/issuer/approval match across package and attestation;
- canonical digest recomputes exactly;
- exact approval decision and authority-basis refs are well formed;
- source and target references are complete;
- acceptance criteria, authority boundaries, verification requirements, Plan assertions, and blueprint graph are valid;
- local target resolution and operator permissions succeed.

Stale, revoked, superseded, draft, review-ready, and merely approved packages cannot enter the import path.
Every top-level acceptance criterion must be referenced by a blueprint. Blueprint
dependency edges must point to a strictly earlier sequence, required approvals must
resolve, and every blueprint must request exactly the package target's code scopes.

## Import behavior

V1 is human-mediated:

1. Authenticated operator chooses the local target and requests preview.
2. Mission Control retrieves and validates the package.
3. It resolves local workspace/project, repository, owner/team, code scopes, and execution workflow semantics.
4. Preview returns the exact draft mapping without state change.
5. Operator confirms the package digest and target.
6. One internal transaction creates the import receipt, Mission draft, Plan draft, and audit events.
7. Existing Mission Control submission and approval flows remain unchanged.

The result is Mission `PLANNING` and Plan `DRAFT`. Import does not submit, approve, compile WorkOrders, dispatch, execute, verify, accept, merge, release, or deploy.

Existing governance remains fail closed. If Plan release is disabled, return `PLAN_RELEASE_DISABLED`. If enabled Mission Spec intake requires a finalized spec/constitution for a new Mission, return `SPEC_INTAKE_REQUIRED`; do not fabricate either record.

## Idempotency

The external key is `(issuer_id, package_id, package_version)`. The receipt stores the digest and resolved target.

- Same key, digest, and target: return the original receipt.
- Same key with different digest or target: return `IDEMPOTENCY_CONFLICT` and create nothing.
- A transport retry reuses the same key; it never silently creates a Plan revision.

## Data minimization

The package transfers only approved execution intent and exact references. Raw uploads, source passages, customer credentials, internal database details, and unrelated customer-model content stay in Factory Engineer. Mission Control validates package references as untrusted provenance metadata, not commands. It persists only the authenticated package URL, mapped draft content, selected requirement IDs, and bounded issuer/package/digest/mapping/correlation receipt metadata; complete upstream reference objects remain in Factory Engineer.

## Error model

Stable bounded failures include:

| Code | Meaning |
|---|---|
| `UNSUPPORTED_CONTRACT_VERSION` | schema or media type is unsupported |
| `INVALID_PACKAGE` | envelope or package content is malformed |
| `PAYLOAD_TOO_LARGE` | response exceeded the importer ceiling |
| `DIGEST_MISMATCH` | canonical digest did not match |
| `ORIGIN_UNVERIFIED` | retrieval authentication, configured issuer, or response binding could not be verified |
| `APPROVAL_UNVERIFIED` | exact upstream authority binding could not be verified |
| `PACKAGE_NOT_PUBLISHED` | immutable/current status not published |
| `PACKAGE_STALE` | published package was withdrawn as stale |
| `PACKAGE_REVOKED` | published package was revoked |
| `PACKAGE_NOT_FOUND` | package version was not found |
| `AUTHENTICATION_REQUIRED` | a Clerk-authenticated Mission Control operator is required |
| `TARGET_NOT_FOUND` | semantic target could not be resolved |
| `TARGET_UNAUTHORIZED` | operator lacks local authority |
| `CODE_SCOPE_REJECTED` | requested scope exceeds local grant/policy |
| `WORKFLOW_UNAVAILABLE` | selected local workflow cannot be used |
| `PLAN_RELEASE_DISABLED` | governed Plan path is not enabled |
| `SPEC_INTAKE_REQUIRED` | local governance requires a finalized Mission Spec |
| `IDEMPOTENCY_CONFLICT` | external identity was reused with different bytes/target |
| `TEMPORARY_UNAVAILABLE` | bounded upstream transport failure |

Errors do not disclose hidden tenant or repository details.

## Actual implementation state

The feature branches implement Factory Engineer package persistence/canonicalization/retrieval and Mission Control retrieval/validation/preview/import. The hosted demo simulates the handoff in browser-local synthetic state and makes zero live requests.

This is not yet a claim of production enterprise identity or operational readiness. Customer launch still requires managed TLS/secrets/rotation, configured issuer allowlisting, deployed service endpoints, production observability, backups, and an approved Mission Control rollout configuration.
