# Authenticated deployment-package retrieval

## Decision

Mission Control retrieves one exact published package version over HTTPS:

```text
GET /api/deployment-packages/{package_id}/versions/{package_version}
Authorization: Bearer <opaque one-time-revealed token>
X-Correlation-ID: <UUID generated by Mission Control>
```

There is no shared database, browser cookie dependency, arbitrary upstream URL, or draft-package access. The endpoint returns the versioned envelope defined in [deployment-package-v1.md](deployment-package-v1.md).

## Credential model

An authenticated engagement owner issues a scoped retrieval grant through:

```text
POST /api/engagements/{engagement_id}/deployment-package-retrieval-grants
```

The owner supplies the requester identity, requester system, and expiry. By default, Factory
Engineer provisions or reuses the canonical dedicated service operator for that engagement and
grants it only `viewer` membership. An existing, separately dedicated service-operator ID may be
supplied for controlled recovery or migration, so more than one dedicated retrieval identity can
exist for an engagement. Cross-engagement reuse and elevated membership are rejected; omitting the
service-operator ID is the normal path.

The opaque token embeds only the service-operator and grant IDs plus random secret material.
Factory Engineer stores SHA-256 of the complete token, never plaintext, and returns the token
only in the successful issuance response.

A grant binds:

- one engagement;
- one active service operator;
- one requester identity and requester system;
- exact scope `deployment-packages:retrieve`;
- expiry, revocation, and creator audit data.

Validation parses a bounded token, applies the embedded operator as PostgreSQL RLS context, loads the exact grant, performs constant-time digest comparison, and checks scope, expiry, revocation, membership, and operator kind/activity. Service identities cannot approve customer truth, readiness, selection, or packages.

Factory Engineer validates the correlation header as a UUID. The exact incoming value is
recorded and returned in the success attestation or bounded denial body; it is never silently
replaced with an unrelated ID.

## Authorization and fail-closed behavior

The service principal may read only package IDs within its grant's engagement. Enumeration outside that boundary returns the same bounded not-found decision available inside the grant; no tenant detail is disclosed.

Retrieval is denied when:

- authentication is missing, malformed, expired, revoked, wrongly scoped, or bound to an inactive service identity;
- engagement deletion is processing or failed;
- the package is absent or outside the grant;
- current state is not `PUBLISHED`;
- immutable status-at-issuance is not `PUBLISHED`;
- digest recomputation fails;
- issuer, approval, source, or publish timestamps are incomplete.

Denied and successful in-scope decisions are committed to the audit trail even though the HTTP response is non-successful. Resolvable invalid, expired, revoked, wrongly scoped, and inactive-service credentials create a general authentication-denial audit event while the engagement is active. Route code must not raise before the audit transaction commits.

## Audit record

Every authenticated package decision records:

- package ID/version and internal version reference when known;
- requester identity/system;
- timestamp, stable result code, digest when known, and correlation ID;
- service actor and engagement in the general audit ledger.

This answers which Mission Control instance requested which immutable package version, when, and with what result. Authentication failures that cannot safely resolve an engagement are logged only through privacy-safe service telemetry; they do not create a cross-tenant domain row.

Resolvable authentication denials record the grant, requester system, stable reason, service
identity, and engagement in the general append-only audit ledger. They do not fabricate a
package retrieval row when no package decision was authorized.

## Provisioning and revocation

V1 exposes issuance and revocation only through owner-authorized operator routes, never through
the public hosted demo:

```text
POST /api/engagements/{engagement_id}/deployment-package-retrieval-grants
POST /api/engagements/{engagement_id}/deployment-package-retrieval-grants/{grant_id}/revoke
```

Plaintext tokens must not appear in request logs, exception detail, database exports, or
data-lifecycle archives.

Grant revocation is immediate for subsequent requests. Rotating a token means issuing a new grant and revoking the prior grant; package versions remain unchanged.

## Production requirements

Before customer deployment:

- terminate TLS at a controlled endpoint and pin the Factory Engineer base URL in Mission Control;
- store the bearer token in a managed secret store and rotate it operationally;
- use production OIDC for human provisioning and a dedicated service identity per target instance;
- alert on repeated denied retrieval, digest mismatch, and revoked-token use;
- retain database backups and audit evidence per customer policy;
- prefer workload identity or mutually authenticated service credentials when the platform supports them.

The deterministic local/test implementation proves scoping, revocation, audit, and contract integrity. It is not represented as a finished enterprise identity platform.
